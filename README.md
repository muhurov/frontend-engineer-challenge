# Advanced Frontend Engineer Challenge

Реализация Auth Flow (регистрация, авторизация, восстановление пароля) для тестового проекта Orbitto Service с использованием [Figma](https://www.figma.com/design/31KetUbya482vMSGgyiNIf/Orbitto-%7C-Service--Copy-?node-id=102-12806&t=TMlkJ3c3j3vJF5fb-4) и [backend](https://github.com/telman03/engineer-challenge).

## Стек

- **React**, **Nextjs**
- **React Hook Form + Zod** — формы + валидация
- **Tailwind CSS** — стили
- **RTK Query** — API

## Запуск проекта

Требования: Node.js **v24+**, Npm **v11+**, Docker (backend)

**Запуск backend:**

Проект использует backend из следующего форка: [https://github.com/telman03/engineer-challenge](https://github.com/telman03/engineer-challenge)

```
git clone https://github.com/telman03/engineer-challenge.git
cd engineer-challenge
docker compose up --build
```

**Запуск frontend:**

```
git clone https://github.com/muhurov/frontend-engineer-challenge.git
cd frontend-engineer-challenge
npm install
npm run dev
```

После запуска frontend будет доступен по адресу:

```
http://localhost:3000/
```

## Архитектура проекта

В проекте используется подход **FSD** с явным разделением на слои и зонами ответственности.

Основная цель — обеспечить:

- масштабируемость
- переиспользуемость
- изоляцию бизнес-логики
- предсказуемую структуру проекта

```
src/
  app/                    # роутинг Next.js
    auth/                 # общий роут для Auth-действий: Login/Reset Password/Forgot Password/Register
      login/              # страница логина
      recover-password/   # страница восстановления пароля (конкретно - этап ввода email для восстановления с соответствующими обработками)
      register/           # страница регистрации
      reset-password/     # страница сброса пароля
    dashboard/            # страница-заглушка для тестирования возможности проверки работоспособности логина и получения информации о текущем юзере, а так же возможность проверки функции логаута в приложении
    providers/            # провайдера для работоспособности связки библиотек
    store/                # настройка сторейджа для хранения данных
  entities/               # бизнес-сущности: auth/session/user
    [entity]/
      model               # константы, слайсы, связанные с сущностью
      api                 # API, связанная с сущностью
      ui                  # UI компоненты сущности
  features/               # готовые бизнес-фичи согласно пользовательским сценариям: (login form, register form, reset password form, recover password form), а также компоненты-гварды: Auth/Guest, которые позволяют перенаправлять пользователя в зависимости от состояния Залогинен-Не залогинен
    [feature]
      model               # константы, валидационные схемы
      lib                 # различные хелперы и утилитные функции
      ui                  # UI-представление фичи
  pages/
    [page]                # полностью работоспособная страница
      ui                  # композиция из фич/компонентов/вызовов апи (где нужно)
  shared/                 # переиспользуемый верхний слой
    api/                  # базовая конфигурация API-клиента
    assets/               # иконки/картинки (не-статика)
    config/               # общие конфигурационные константы и тд
    lib/                  # общие переиспользуемые хелперы, функции, хуки и тд
    ui                    # базовые переиспользуемые компоненты
```

## Решения

- Было принято решение немного отойти от макета и сделать общий лэйаут для всех этих страниц из Auth Flow (с лого в правой части страницы - как для Login/Register страниц)) - для сохранения общности внешнего вида в рамках одного Flow
- Было добавлены компоненты-гварды (Auth/Guest), которые занимаются проверкой существования данных о текущем юзере и соответствующим редиректом на доступные страницы:
  - если залогиненный юзер попадает на какую-либо страницу авторизации - он перенаправляется на Welcome-страницу (в нашем случае - Dashboard)
  - если незалогиненный юзер попадает на какую-либо из описанных "приватных" страниц - он перенаправляется на логин
- Было решено отказаться от использования готовых UI-фреймворков в пользу того, что внешний вид приложения довольно минималистичен и не требует лишнего оверхеда в виде тонны ненужных компонентов. Тем не менее, архитектура приложения и в целом общих используемых компонентов предоставляет возможность в любой момент добавить в приложение нужную библиотеку и немного дописать код для миграции текущих контрактов на библиотечные, при этом не меняя концепцию
- Для хранения access/refresh токенов используется localStorage (дефолтный вариант при отсутствии Cookies+HttpOnly на стороне бэкенда).
- Tailwind CSS использован как минималистичный (в плане бандла - умеет вырезать ненужное) и довольно строгий в плане описания, но при этом легко расширяемый, а так же избавляющий от лишних css-файлов и траты времени на придумывание классов

## Trade-offs

- Dashboard
  - представлена только как базовый шаблон для 'Private'-роутов, с возможностью посмотреть данные текущего юзера (для проверки работоспособности логина) и вылогиниться
- Контракты Backend
  - в эндпоинт для запроса токена для сброса пароля в ответ хотелось бы добавить поле email - юзера, который запросил пароль - это бы избавило от оверхеда на странице сброса по пробросу наверх этого поля, а так же при реализации перехода по ссылке из письма (которое будет приходить в production) позволит унифицировать подходы фронтэнда и бэкенда к реализации данной фичи
  - обработка ошибок базируется на поле `message`, которые к тому же имеют разный формат от сообщение к сообщению, поэтому пришлось принять решение временно сделать кашу: сообщения с сервера, которые соответствуют конкретному формату, - отображать, остальные показывать как есть; еще до стадии production хотелось бы обсудить с бэкендом стратегию ведения ошибок на фронт (как самый удобный вариант, в т. ч. и в плане возможной интернационализации на фронте - избавление от поля message (где это возможно), и добавление поля type, по которому фронт мог бы однозначно определить ошибку и отобразить нужные сообщения в нужном формате в любом месте приложения)
